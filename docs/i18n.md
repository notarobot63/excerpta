# Internationalisation (i18n)

Architecture decision for translating the Excerpta interface.
Status: **decided**. Date: 2026-07-26.

This document sets the rules. Read it in full before contributing anything that
touches interface strings.

---

## 1. Decision

**Source strings (`msgid`) are written in English.**

French is a translation catalogue like any other (`fr.po`), on equal footing
with Italian or Polish.

```
# Chosen
msgid "Add link"
msgstr "Ajouter un lien"      # in fr.po

# Rejected
msgid "Ajouter un lien"
msgstr "Add link"             # in en.po
```

### Why

The project is open to contributors of every language. Had the `msgid` stayed
in French, producing `es.po` would have meant translating *from French*, which
would restrict the pool of translators to French speakers and defeat the
purpose.

### What it costs

- A one-off rewrite of every interface string into English, with the existing
  French moved into `fr.po`.
- A standing discipline: every new string is written in English in the code,
  and its French translation is added to `fr.po` afterwards.

---

## 2. Scope

### Translated

- Every template under `app/templates/`.
- User-facing messages in `app/` rendered as HTML.
- Date and number formats, through `babel.dates` / `babel.numbers`.

### Deliberately not translated

- **User content**: link titles and descriptions, Markdown notes, folder and
  tag names. That is data, not interface.
- **JSON API responses** (`/api/v1/*`). Their `detail` fields are consumed by
  clients, including the Android app. They stay in fixed English and never go
  through gettext, because translating them would break the API contract.
- **CSS theme names**.
- **Server logs**, which stay in English.

## 3. Technical choices

### Tooling

| Item | Choice |
|---|---|
| Format | gettext (`.po` source, `.mo` compiled) |
| Extraction / compilation | Babel (`pybabel extract` / `init` / `update` / `compile`) |
| Template integration | `jinja2.ext.i18n` (ships with Jinja2, no extra dependency) |

### Locale resolution: never global state

The locale is **request state**, not application state.

`gettext.install()`, and any `Translations` object bound once and for all to the
Jinja environment, are **forbidden**. In an async application serving concurrent
requests, an English request would then be rendered with the locale of a French
request handled in parallel.

How it works instead:

1. A `ContextVar` holds the current locale. `contextvars` guarantees isolation
   per asyncio task.
2. An HTTP middleware resolves the locale at the start of each request and sets
   that `ContextVar`.
3. The Jinja environment in `app/templates_cfg.py` registers `gettext` /
   `ngettext` callables that **read the `ContextVar` on every call**, rather
   than capturing a translation at startup.

Middleware placement: it must run *after* `SessionMiddleware`, since the signed
in user's preference is read from the session. Because Starlette pushes each
`add_middleware` onto the front of the stack (the last one added runs first),
that means adding it *before* `SessionMiddleware` in `app/main.py`.

`test_concurrent_tasks_do_not_share_locale` guards this design. Replacing the
`ContextVar` with global state makes it fail, which is exactly the bug the
design exists to prevent.

### Resolution cascade

First match wins:

1. Signed in user's preference (`User.language`).
2. The `lang` cookie, for anonymous visitors on public pages (`/u/{slug}`) and
   the sign-in page.
3. The browser's `Accept-Language` header.
4. Default: `en`.

The language selector must be reachable **before** signing in. A visitor
discovering the service judges the interface before having an account to attach
a preference to. It therefore sits on the sign-in page and on public pages.

Once signed in, the setting lives in **Settings**, next to appearance: it is an
account setting, like the theme, not a control used all the time. The
`_lang_picker.html` partial therefore renders two shapes depending on
`lang_picker_full`: compact codes (`EN · FR`) on pages with no settings screen,
full language names in Settings.

The session is populated at sign-in, not on every request: the middleware must
never hit the database. Two deliberate consequences, in `app/routes/oidc.py`:

- the stored preference is copied back into the session after the rotation's
  `session.clear()`, otherwise it would be ignored until the next visit;
- if the visitor picked a language **before** signing in, that choice is
  adopted as the account preference rather than lost at login.

### Changing language: a GET route

`GET /lang/{code}` is an exception to the project rule that every state change
goes through POST + CSRF. This is deliberate:

1. The action is benign and idempotent, it only changes what is displayed.
2. A CSRF-protected POST would require `csrf_input()` on the sign-in page and
   on public pages, and therefore a session cookie for **every anonymous
   visitor**.
3. A link works without JavaScript, including on standalone pages that do not
   load `app.js`, and the CSP forbids inline handlers.

The residual risk is a third party changing what language a visitor sees. The
redirect, on the other hand, is strictly validated: `safe_next()` rejects any
non-internal target, without which the route would be an open redirector. This
is covered by `test_safe_next_refuses_anything_external`, including
`//evil.example` and `/\evil.example`, which browsers read as hosts.

### Plurals

Any string containing a counter goes through `ngettext`. "1 link" and "5 links"
are not the same string, and some languages have more than two plural forms.

### Writing pitfalls

`newstyle` mode applies `string % variables` after translation. Three
consequences, all verified:

- **A literal `%` must be doubled.** `_("100% done")` raises a `TypeError` at
  render time; write `_("100%% done")`.
- **Renaming a variable in a translation breaks the page.** `%(nb)d` where the
  `msgid` says `%(num)d` raises a `KeyError`. This is checked by
  `test_catalog_placeholders_survive_translation`.
- **Omitting a variable, on the other hand, is fine.** A singular form may do
  without the counter.

Also avoid HTML entities inside `msgid`: write `{{ _("Checking") }}&hellip;`
rather than `{{ _("Checking&hellip;") }}`, so translators never have to handle
markup.

### Strings in Alpine.js

Alpine is written inline in the templates. Any visible string appearing in an
`x-text`, a `:title` or similar must be produced on the Jinja side through
`_()`, never hardcoded in the JavaScript expression. A hardcoded string escapes
`pybabel extract` and will only ever be found by a translator.

The pattern is to declare the string at the top of the script, serialised with
`|tojson`:

```js
var rootLabel = {{ _("- None (top level) -")|tojson }};
```

**Known limitation, for client-side plurals.** When the counter is computed in
the browser (number of selected links), the server cannot pick the plural form.
Both forms are then pre-translated and the choice is made in JavaScript on
`n > 1`:

```js
var LBL_SELECTED_ONE = {{ ngettext("{n} link selected", "{n} links selected", 1)|tojson }};
var LBL_SELECTED_MANY = {{ ngettext("{n} link selected", "{n} links selected", 2)|tojson }};
```

The `{n}` token is substituted client-side. This pattern only renders correctly
for languages with two plural forms: Russian or Polish, which have three, will
be approximate at those specific spots. Fixing it would require a JavaScript
i18n library, which is not worth it for two strings.

### Catalogue versioning

- `.po` files are versioned in git. They are what contributors edit.
- `.mo` files are **not versioned**. They are compiled at build time by
  `pybabel compile` in the `Dockerfile`.

Rationale: templates and static assets are baked into the Docker image.
Versioning compiled binaries would produce unreadable diffs in review and risk
stale `.mo` files.

### Layout

```
app/
  translations/
    fr/LC_MESSAGES/messages.po
    <locale>/LC_MESSAGES/messages.po
  messages.pot                      # extracted template, regenerated
babel.cfg                           # jinja2 + python extractors
```

`en` has no catalogue on purpose: the `msgid` *are* the English text, so a
catalogue would be an identity mapping. `available_locales()` always offers
`en` regardless of what is on disk.

## 4. Adding or updating a translation

```bash
pip install -r requirements-dev.txt

# Refresh the template from the source code
pybabel extract -F babel.cfg -o app/messages.pot --project=Excerpta .

# Start a new language (once)
pybabel init -i app/messages.pot -d app/translations -l it

# Or update an existing one after new strings appeared
pybabel update -i app/messages.pot -d app/translations -l it

# Compile locally to check your work (the .mo is not committed)
pybabel compile -d app/translations
```

Edit `app/translations/<locale>/LC_MESSAGES/messages.po` with any text editor
or a dedicated tool such as Poedit, then open a pull request with the `.po`
file only.

`pytest tests/test_i18n.py` validates catalogue integrity before you submit.

## 5. The two branches

The repository has two branches that cannot be merged:

- `github-main` on GitHub, English documentation, no demo mode. **This is the
  branch translation contributions go to.**
- `main` on a private GitLab, French documentation, includes the demo mode.

A new language catalogue is a standalone file with no dependency on the rest of
the code, so moving it from one branch to the other is a file copy, not a merge.
It is the kind of contribution that suffers least from the divergence.

Catalogues differ slightly between branches: strings belonging to the demo mode
only exist on `main`, and are left untranslated there when a catalogue is
copied over. They then show in English, the source language.
